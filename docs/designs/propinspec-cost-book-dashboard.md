## Problem Statement
`/cost-book` is one long page: GPM Labor, Materials (General purchase history + the just-shipped Stock Items), and Vendor Estimates all stacked in sequence. As more sections land (Stock Items just added this session), the page is getting harder to navigate — confirmed directly by Jessica's team, not just an assumption about the page's growth.

## Demand Evidence
Direct, not inferred: "Jessica or her team specifically said it's hard to find things" (Q5 answer). This is the same team whose real, observed workaround behavior (typing correct stock prices from memory) drove the Stock Items design earlier this session — a team that is actively using this page daily, not a hypothetical future user.

## Status Quo
Confirmed (Q2, pushed twice): "Everything lives in one Cost Book page today" → the actual cost is "the page itself is getting hard to navigate," not missing data coverage. Home Depot pricing (`cost_book_materials`, ~8,150 rows) already carries a `source` text field, currently always `'Home Depot'` in practice; no Lowe's or other-supplier data exists yet, but that absence was explicitly ruled out as the primary pain point this session.

## Target User & Narrowest Wedge
Target: Jessica and her team, same as every Cost Book session this cycle. Narrowest wedge (Q4, confirmed): reorganizing the SAME existing data into a landing dashboard + sub-book pages fixes the real, confirmed problem on its own — the receipt/invoice import generalization and the supplier-website search popup are NOT required for this fix to be worth shipping.

## Constraints
- **Zero migration of the 8,150 live `cost_book_materials` rows.** The reorg (and the new Suppliers catalog below) must work by filtering/validating the existing `source` column, not by moving data into new per-supplier tables.
- **The live supplier-search popup stays out of scope — 4th deferral.** The user's original request generalizes the popup idea to "any supplier's web site," but the underlying blocker is unchanged and now broader: Home Depot has no official API and actively blocks direct scraping (confirmed via a real 403 test, `propinspec-cost-history.md`), and nothing in this session's evidence suggests Lowe's or another retailer differs. A live popup search across N suppliers is N vendor-scraper integrations, not one — a bigger version of a decision already deferred 3 times (`quote-sheet-bulk-item-auto-fill.md`, `propinspec-cost-history.md`, `propinspec-stock-items.md`). Still not this wedge.
- **Receipt/invoice import per sub-book is a real, separable follow-on**, not part of this wedge. `scripts/import-cost-history.mjs` already proves the CSV-import pattern for Home Depot, but a Lowe's (or other supplier) export's real column layout, header quirks, and currency formatting are unknown until a real sample file is seen — the Home Depot CSV had a 6-line preamble and embedded quote-mark characters discovered only by reading the actual file. Building a Lowe's importer from assumption, without a real export in hand, risks the same kind of wasted-build outcome the GPS-metadata probe was built to avoid earlier this session.
- **"Sub-book" must be a real, defined concept, not a label.** Per Premise 3: Labor (`cost_book_gpm_labor`) and Vendor Estimates (`cost_book_vendor_estimates`, trade/contractor placeholders) are GPM's own internal cost tables, not supplier catalogs — they don't have a `source`/supplier column and were never going to. Stock Items (`stock_items`) is GPM's own curated list; its `supplier` column defaults to Home Depot but the table itself isn't a supplier-import target. Only `cost_book_materials` (General history) is genuinely supplier-scoped data today.

## Approaches Considered
### Approach A: View-only reorg, zero schema changes
Dashboard landing page + sub-pages (`/cost-book/labor`, `/cost-book/stock-items`, `/cost-book/suppliers/[name]` — same route naming as the chosen Approach B below) built as filtered views into the 4 existing tables. "Add another supplier" stays informal — typing a new string into the existing `source` field on Materials. Effort: S (human ~2 days / CC ~1 hr). Rejected as the sole approach: doesn't give admins a real place to manage the supplier list, which is what the user actually asked for ("ability to add other suppliers").

### Approach B: Dashboard + sub-pages backed by a new Suppliers catalog (CHOSEN)
Same page reorg as A, plus a new `suppliers` catalog table (same pattern as `vendors`/`inspection_types`/`inspectors` — admin-managed, name + optional notes). `cost_book_materials.source` gets validated/autocompleted against it instead of staying pure freeform text; no migration of existing rows (a backfill upserts `'Home Depot'` into the new catalog once, existing rows are untouched). Effort: M (human ~3-4 days / CC ~3-4 hrs — revised up after review; see Data Model and The Assignment for the full scope this covers: migration, dashboard aggregation queries, a new dynamic route reusing/refactoring the existing drill-down code, Labor+Vendor-Estimates merge, datalist wiring with collision validation, the rename action with its transactional cross-row cascade and disposable-test-data verification, and mandatory real-data verification of everything else).

### Approach C: Full re-architecture into per-supplier tables
Split `cost_book_materials` into real per-supplier tables (or a `supplier_materials` table with a `supplier_id` FK), replacing the single flat table. Effort: L (human ~1-2 weeks / CC ~4-6 hrs). Rejected: real migration risk to 8,150 live production rows, for a problem confirmed to be navigation, not data-model correctness — over-building for the actual complaint.

## Recommended Approach
Approach B. Chosen by Chris.

## Data Model
- **New table `suppliers`**: `id uuid`, `name text not null`, `notes text`, `created_at`. **Case-insensitive uniqueness** — a functional unique index on `lower(name)` (same technique as `stock_items`' `(lower(category), lower(material_name))` index from this session's prior wedge), not a plain case-sensitive `unique` column. Without this, `'Home Depot'` and `'home depot'` could both be inserted as distinct rows, each capturing only exactly-matching `source` values and silently fragmenting one supplier's materials across two tiles — a review-caught gap, not a hypothetical. Same pattern as `vendors`/`inspection_types`/`inspectors` (`app/setup/*`) otherwise. Seeded once via backfill with the distinct `source` values already present in `cost_book_materials` (in practice, just `'Home Depot'` today) — not a migration of the materials rows themselves, just populating the new lookup list from what's already there.
- **`cost_book_materials.source` matching is case-insensitive too**: dashboard tile counts and the `/cost-book/suppliers/[name]` filter both compare `lower(source) = lower($name)`, so a row's exact casing never determines whether it's found.
- **Orphaned/unmatched `source` values, explicitly resolved**: saving a material (via the existing add/edit form, or any future import) with a `source` value that doesn't yet exist in `suppliers` (case-insensitively) auto-creates that `suppliers` row inline, the same "create on first use" behavior Stock Items' `category` field already has. This means every material is always reachable from some tile — there is no unmatched/invisible state to design around, because the set of tiles is *derived from* the materials data (distinct `source` values), not a separate list that data must conform to.
- **`suppliers` is add/rename-only in this wedge, no delete.** Renaming is a real, explicit capability (not deferred) precisely because materials aren't FK'd to it: a rename updates every `cost_book_materials` row whose `source` case-insensitively matched the old name, in the same transaction, so the two never desync. Delete is left out of this wedge — deleting a supplier with materials still attached raises the same "what happens to those rows" question a delete on `inspection_types` already has to guard against (see `deleteInspectionType`'s in-use check), and nothing in this session's evidence says GPM needs to remove a supplier yet; add it if that need shows up.
- **Add Supplier on a case-insensitive name collision**: rejected with an inline validation error naming the existing supplier (e.g., "A supplier named 'Home Depot' already exists") rather than a silent no-op or a raw DB unique-violation error — same user-facing pattern as `createInspector`/`createVendor`'s `on conflict ... do nothing` today, except the admin needs to actually see why nothing happened here since they were trying to add a distinct-looking name.
- **Landing dashboard** at `/cost-book`: short intro paragraph (per the user's request) + a card/tile per sub-book — Labor & Vendor Estimates combined (rate count + estimate count, both surfaced on one tile per Premise 6's resolution below), Stock Items (item count), and one tile per row in `suppliers` (material count for that source) — each linking to its own page. An "Add Supplier" action on the dashboard writes to the new `suppliers` table (admin-gated, same as every other catalog mutation in this app).
- **Sub-book pages:**
  - `/cost-book/labor` — today's GPM Labor section AND Vendor Estimates section, both moved here unchanged (Premise 6 resolution: both are GPM-internal cost-estimate tables, not supplier catalogs, so they share a home rather than being force-fit into the supplier list).
  - `/cost-book/stock-items` — already exists (shipped this session), just gets a card/link from the new dashboard; no changes to the page itself.
  - `/cost-book/suppliers/[name]` — the existing Materials section's Department/Class/Subclass search/filter UI, now scoped to `where lower(source) = lower($name)` instead of showing every supplier's rows on one page. This UI is **not Home-Depot-specific** despite `department_name`/`class_name`/`subclass_name` being populated from Home Depot's own taxonomy today (`propinspec-cost-history.md`) — those columns are just text, and the search box already handles the general case. A newly added supplier with zero materials renders the same page with an empty state ("No materials yet — add one below" — the existing empty-state copy already on `/cost-book` today), not a broken or missing page; its own category values (if any) populate the drill-down naturally as materials are added under it.
- **Old `/cost-book` page's current content is fully replaced** by the dashboard above. Checked for deep links into the old page beyond its top-level URL: only two exist in the codebase (`app/components/AppShell.tsx`'s nav item and `app/setup/page.tsx`'s System Config hub link), both plain `/cost-book` with no section anchor or query param — both keep working unchanged since the dashboard replaces the page's content at the same URL, not the URL itself.

## Open Questions

## Success Criteria

- Renaming a supplier updates every material's `source` that matched it — verified against a **test/synthetic supplier only** (e.g., a manually added "Test Supplier — Delete Me" with a couple of manually added materials, same disposable-test-data discipline as the Stock Items wedge's live verification), never by renaming the real "Home Depot" supplier — a bug in a brand-new bulk cross-row UPDATE is not something to first discover against the live 8,150-row table.

- No regression: Quote Sheet suggestion flow (`suggestHistoricalCost`, `runAutoBuildQuote`, Stock Items) is unaffected — none of those touch the `source` column's freeform-vs-catalog status in a way that changes matching behavior.

### R3-1 — completeness

**Problem**

> Data Model specifies that renaming a supplier cascades to matching cost_book_materials rows and is protected by a case-insensitive unique index on suppliers.name (lower(name)), but never specifies what happens when an admin renames a supplier to a name that case-insensitively collides with a different, already-existing supplier (e.g., renaming 'Home Depot' to a name that matches an existing 'Lowe's' row). Given the unique index, an unguarded rename attempt would hit a raw DB unique-violation error unless a specific UX is chosen. This is the same class of gap R2-2 raised for the Add Supplier path (now resolved with an inline validation error naming the existing supplier), but for the distinct Rename code path, which remains unaddressed.

**Remedy**

> Specify the Rename UX for a case-insensitive collision with a different existing supplier (e.g., the same inline validation error pattern chosen for Add Supplier, or an explicit merge behavior), and add a corresponding Success Criteria verification step.

### R3-2 — clarity

**Problem**

> The document specifies the rename action's backend behavior in detail (cascading UPDATE across cost_book_materials, same transaction, test/synthetic-data-only verification) and explicitly locates the Add Supplier control ('An "Add Supplier" action on the dashboard writes to the new suppliers table'), but never states where or how an admin actually invokes a rename — no control is described on the dashboard tiles, the /cost-book/suppliers/[name] sub-page, or elsewhere. Admin-gating is stated explicitly for Add Supplier ('admin-gated, same as every other catalog mutation in this app') but is never confirmed for Rename.

**Remedy**

> Specify where the rename control lives in the UI (e.g., an edit affordance on each dashboard tile or on the supplier's sub-book page) and confirm it is admin-gated like every other catalog mutation.

### R3-3 — completeness

**Problem**

> Constraints states Stock Items' 'supplier column defaults to Home Depot' as a real column on the stock_items table, distinct from cost_book_materials.source. The Data Model's rename cascade is scoped explicitly to 'every cost_book_materials row whose source case-insensitively matched the old name' — stock_items.supplier is never mentioned. After a supplier rename, the suppliers catalog's canonical name and cost_book_materials.source would update together, but stock_items.supplier would retain the stale old name, reintroducing on a second table the exact fragmentation/desync problem the case-insensitive unique index and rename cascade were built to prevent on the first.

**Remedy**

> Decide and document whether renaming a supplier also updates matching stock_items.supplier values in the same transaction, or explicitly accept the resulting staleness as out of scope with a stated reason.

### R3-4 — completeness

**Problem**

> Data Model specifies that Add Supplier on a case-insensitive name collision must be rejected with an inline validation error naming the existing supplier (the R2-2 fix). Success Criteria, however, never includes a verification step for this specific behavior — it verifies a successful add ('Lowe's'), case-insensitive material-to-tile matching, and the rename cascade, but not the collision-rejection path itself, leaving a now-specified behavior without a corresponding acceptance check.

**Remedy**

> Add a Success Criteria bullet verifying that adding a supplier whose name case-insensitively collides with an existing one (e.g., typing 'home depot') is rejected with the inline validation error, not silently ignored or surfaced as a raw DB error.
