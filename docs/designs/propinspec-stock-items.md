## Problem Statement
The Cost Book's material-cost suggestion (`suggestHistoricalCost`/`runAutoBuildQuote`) runs one embedding-similarity search against all ~8,150 unique historical Home Depot SKUs. For GPM's own deliberately-stocked rehab items — outlets, switches, covers, light bulbs, smoke detectors, batteries, caulk, lights, fans, door hardware, lock sets, and similar — that search is noisy specifically because the table holds many near-duplicate historical purchases of the "same" item type (different SKUs, different prices, different descriptions across two years of receipts) with no signal for "this is the one GPM actually standardized on." There usually is one right answer for these items; the current design has no way to say so.

## Demand Evidence
Secondhand, not observed directly — Chris has had multiple conversations with Jessica about this, not watched her work (confirmed via Q5: "Not directly — this is from conversations with Jessica, not watching"). The real behavioral evidence that does exist: when the current suggestion is wrong for a stock item, Jessica's team catches it and manually types the correct price from memory, every time (Q2, pushed twice: "Suggest from history gives noisy/wrong matches for stock items specifically" → "They catch it and manually type the right price every time"). This has never let a wrong price reach a real quote — the cost so far is friction/override work, not a financial error.

## Status Quo
One `cost_book_materials` table (~8,150 SKUs from the September 2026 Home Depot Pro Xtra CSV import, see `propinspec-cost-history.md`), one embedding-similarity search, one 0.75-cosine-similarity cutoff, applied uniformly to every line item regardless of whether it's a commonly-stocked item or a genuine one-off. Reviewers manually override bad stock-item suggestions today; there is no mechanism that turns that manual correction into anything permanent — the same wrong suggestion recurs next time.

## Data Model
- **New table `stock_items`**, not a flag on `cost_book_materials` (Chris's explicit choice — Option B over the flag-based Option A): `id uuid`, `category text not null`, `material_name text not null`, `supplier text not null default 'Home Depot'`, `sku text`, `unit_price numeric(10,2) not null`, `unit text`, `notes text`, `embedding vector(768)`, `created_by text`, `created_at`, `updated_at`. **`unique (category, material_name)`** (case-insensitive, via a generated lower-cased column or a functional unique index) — this is the upsert key for promotion (below); without it, repeatedly promoting the same corrected item — the exact recurring-correction scenario this feature exists for — would insert duplicates instead of updating one row. Total separation from the 8,150-row General history — nothing here is touched by the CSV import or its backfill.
- **Matching still uses embeddings — same technique, cleaner data.** The noise in the current system comes from the *General* table holding many near-duplicate rows per item type, not from embedding similarity being the wrong technique. `stock_items` reuses the exact same `gemini-embedding-001` (768-dim, Matryoshka-truncated) + pgvector HNSW cosine-index pattern already built for `cost_book_materials` (`lib/embeddings.ts`). Because each Stock Item is intentionally singular per item type, a match against this table is far less ambiguous than the same search against General — this is the actual fix, not a new matching algorithm.
- **Suggestion flow gets a first-check branch — same trigger contract each function already has, not a new uniform behavior:**
  - `suggestHistoricalCost` (actions.ts) only ever returns candidate suggestions, never writes — that's true today for General and stays true for Stock Items. The first-check branch searches `stock_items` first; a hit is returned as a suggestion (labeled "Stock Item match," distinct from a "Historical Purchase match"), same as today. No hit falls through to the existing General search.
  - `applyHistoricalCostSuggestion` is the actual write path, fired only on the reviewer's explicit click, exactly as today — it needs to accept a Stock Item as its source (reading `supplier`/`sku`/`unit_price` as real values instead of today's hardcoded `supplier = 'Home Depot'` literal, since a promoted Stock Item's supplier may not always be Home Depot).
  - `runAutoBuildQuote` already auto-writes any match ≥0.75 today, unchanged behavior — a Stock Item hit ≥0.75 is written the same way a General hit is today, just checked first. This function needs the same hardcoded-supplier fix as above.
  - Net: two existing write call sites (in `applyHistoricalCostSuggestion` and `runAutoBuildQuote`) get real edits to read a variable supplier, not just a bolted-on branch — more than a one-line addition, but no change to either function's confirm-vs-auto-apply contract.
- **"Save as Stock Item" promotion**, via a new `promoteToStockItem` server action reachable from the Quote Sheet line item wherever Supplier/SKU/materials-cost is manually typed or overridden. **Not admin-gated** — it must use the same auth check as the existing Quote Sheet save action it's attached to (`updateQuoteSheetItems`, which only requires a logged-in session, not admin), otherwise the one action this whole wedge is built around would be unusable by whichever reviewer role actually edits Quote Sheets day to day. Upserts on `(category, material_name)` (category field with autocomplete, defaulting to blank/last-used). Embedding generation happens inline at write-time; **on a Gemini call failure, the row still saves with `embedding = null`** (same null-on-failure + backfill convention already established for the General import — a promoted item just won't surface via similarity search until backfilled, but the reviewer's correction is never lost or blocked by an API hiccup).
- **New Cost Book "Stock Items" page** (`dashboard/app/cost-book/stock-items/`, linked from the existing Cost Book nav): browse/search/edit/delete by category. This admin page is where **admin-gating does apply** — direct catalog curation (fixing a bad promotion, merging a duplicate, pre-seeding a known item) stays admin-only, same pattern as Inspectors/Inspection Types/Properties, even though promotion itself (above) is not admin-gated.

## Premises
1. The wholesale SKU-import + embedding-similarity match is fundamentally wrong for GPM's own deliberately-stocked categories — it optimizes for "sounds similar to a past purchase," not "the exact item GPM standardized on." **AGREED.**
2. The existing ~8,150-SKU historical import stays valuable as-is for General/one-off items, where embedding similarity is the right tool because there's no single canonical answer. **AGREED — not replaced, not touched.**
3. **Revises** `propinspec-cost-history.md` Premise 3 ("`cost_book_materials` is... not superseded by a separate parallel list"): Stock Items *is* that separate parallel list, deliberately, for the subset of material types where a single canonical answer actually exists. General import stays the source of truth for everything else.
4. A live Home Depot product search/picker needs a paid third-party scraper API — a real, unresolved vendor decision, deferred three times now (bulk-item-auto-fill doc, cost-history doc, this doc) — not something this wedge builds toward or depends on. **AGREED.**
5. The Stock Items catalog is built FROM the quoting workflow itself (a "Save as Stock Item" action on whatever SKU/price/category a reviewer just typed), not from a Home Depot search popup — zero new integration, captures the exact moment Q2/Q3 showed already happens today. **AGREED.**
6. Labor-cost auto-suggestion is a real, named gap against Chris's stated long-term goal but explicitly out of scope for this wedge. **NAMED, not addressed here.**

## Approaches Considered (structural — decided via direct choice, not exploration)
### Option A: flag on existing `cost_book_materials` table (not chosen)
`is_stock boolean` + `stock_category text` columns on the existing table; matching logic branches on the flag before falling back to full-table search. Effort: S (human ~1 day / CC ~20 min). Rejected: Stock Items would still live inside the same 8,150-row table it's meant to escape — a stray CSV re-import or backfill could touch stock rows; browsing/curating the stock subset means filtering a giant table rather than a clean, small one.

### Option B: dedicated `stock_items` table + catalog page (CHOSEN)
As specified in Data Model above. Effort: M (human ~4-6 days / CC ~2-4 hrs) — revised up from the original Phase 4 estimate after review surfaced real scope: the write-path edits touch two existing functions' hardcoded supplier handling (not just an added branch), the promotion action's auth/upsert semantics needed pinning down, and the catalog page is full CRUD + search + category autocomplete, not the simpler add/delete-only shape of the Inspectors page it's patterned after. Total separation from General; a real page for Jessica to manage the list directly.

### Option C: dedicated table, promotion-only, no catalog page (considered, not chosen)
Same table as B, skip the admin page for v1 — Stock Items only ever created via promotion. Effort: S-M (human ~2-3 days / CC ~1-1.5 hrs). Not chosen: Chris picked B directly, valuing Jessica's ability to curate/pre-seed/fix entries over the smaller build.

## Success Criteria
- Migration creates `stock_items` with the embedding column, the `unique (category, material_name)` constraint, and an HNSW index; table starts empty (no forced pre-seed).
- `suggestHistoricalCost` returns a distinctly-labeled "Stock Item match" ahead of any "Historical Purchase match," still confirm-only (no auto-write); `runAutoBuildQuote` auto-applies a Stock Item hit ≥0.75 the same way it already auto-applies General hits today — verified against a real stock-item example (e.g., a smoke detector) after at least one promotion.
