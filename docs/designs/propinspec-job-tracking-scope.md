## Problem Statement

PropInspec's inspection→quote pipeline (Turn Scope sheet, Move Out Report) is approved and in active internal use at GPM. The question this session addresses: GPM wants to extend PropInspec to track the rehab/turn *job* itself, from quote through completion — not just generate the quote document. Should that live fully integrated inside PropInspec, or as a separate tool that links to it? And how does that choice affect marketing PropInspec to other property management companies?

## Demand Evidence

Concrete workflow, from the user directly: after PropInspec generates the Quote Sheet, it is handed (as a hard copy) through a chain — maintenance supervisor assigns labor hours → Courtney hand-writes materials pricing and calls vendors for quotes, hand-writing their responses → Jessica + maintenance lead review for gaps → Courtney re-enters a summarized version into a separate owner-facing quote template → Jessica/Angel schedule GPM crews while Courtney separately calls vendors with schedule windows (some vendor work must finish before GPM work starts) → a spreadsheet "somewhat tracks" this schedule but is "not very workable for the entire staff" → QC inspection → filed. A concrete scheduling failure has already happened (confirmed, not hypothetical) from lack of shared visibility.

Notable: even though PropInspec now generates a real digital Quote Sheet, the described workflow still treats it as printed/hand-written-on paper at several steps — the digital artifact hasn't yet displaced the paper habit at the point of use.

## Status Quo

The job-tracking piece has no working system today. Courtney's spreadsheet is the closest thing, and it's explicitly not workable for the whole staff — this is the same rekey-and-relay drudgery already quantified in the original design doc's Status Quo table, just one stage further downstream (post-quote instead of post-inspection).

## Approaches Considered

### Approach A: In-app Job Timeline, staff-only — RECOMMENDED
Add four fields to the existing `line_items` table (same DB, same app, no new tables):
- `status` — enum, one of `not_started` / `scheduled` / `in_progress` / `blocked` / `done` / `qc_needed`. Existing rows default to `not_started` on migration; nothing is backfilled for already-completed historical inspections.
- `scheduled_start`, `scheduled_end` — plain `date` (not datetime — the described workflow gives vendors a schedule window, a day, not a specific time).
- `blocks_line_item_id` — nullable self-FK, meaning "this line item must be completed before the referenced one can start" (predecessor pointer). Models a **single predecessor only**; a real dependency with multiple blocking trades (e.g. drywall waiting on both plumbing and electrical) is represented as a chained pair of single-predecessor links, not a true many-to-many graph. Accepted MVP simplification — revisit if that case turns out to be common rather than rare.

UI: one new per-inspection **timeline view** (rows = line items, a draggable horizontal bar per item spanning `scheduled_start`→`scheduled_end`, visually flagging `blocks_line_item_id` dependencies) — deliberately not a kanban/status board, since the diagnosed problem is sequencing visibility ("vendor X must finish before crew Y starts"), which a plain status list doesn't show. Staff-updated only (Jessica/Angel/Courtney) — no vendor login, no new permission system. Effort: M (revised from S-M after eng review — see Engineering Review Decisions below). Risk: Medium (revised from Low — drag-to-reschedule is a new client-interaction pattern for this codebase).
- Reuses 100% of existing schema and auth.
- Targets the exact evidenced failure (sequencing visibility) with the smallest surface that could plausibly fix it.
- Doesn't yet solve the "vendor doesn't see their own schedule" half — Courtney still relays by phone, same as today.
- Single-predecessor data model is the one place effort/risk could be optimistic if real dependencies turn out to be many-to-many more often than expected.

### Approach B (Job-Domain): Full Jobs domain, built to extend later
New first-class `jobs` table modeling a full turn lifecycle (incl. QC and City C of O steps), calendar+timeline+list views, structured for a future vendor-facing layer behind its own auth. Not to be confused with the original PropInspec design doc's own "Approach B" (the multi-tenant sellable platform). Effort: L. Risk: Medium.
- Models the real domain completely, including the City C of O wrinkle.
- **Rejected for now** — commits real build time to a domain with zero external validation and one internal failure as evidence; repeats the platform-before-demand risk Premise 3 already flags.

### Approach C: Auto-synced Google Sheet, no new UI
Reuse the existing Drive/Sheets integration (already built for Turn Scope) to auto-generate a live per-property status/schedule Sheet from the DB, instead of a new app screen. Effort: S. Risk: Low.
- Near-zero build cost, tests the "shared visibility" hypothesis before committing to a UI.
- **Rejected for now** — GPM's current broken solution is already a spreadsheet; the complaint was about workability for the whole staff, which auto-generating it doesn't obviously fix.

## Recommended Approach

**Approach A.** Ship the smallest staff-only fix for the specific evidenced failure (sequencing visibility) inside the existing app and database — no new architecture, no vendor-facing surface yet, no external marketing yet. This is the same sequencing discipline the original design doc already used for the inspection piece: prove internally, in production, before expanding scope.

## Engineering Review Decisions (2026-09-11, /plan-eng-review)

Scope and schema decisions made against the approved Approach A, before implementation:

- **Scope is per-inspection, not per-property.** No `properties` table exists (`property_address` is free text on `inspections`) — the timeline is one inspection's line items, same unit as every other view in this app. A re-turn of the same physical property is a separate inspection with its own timeline, not a merged view. This makes "cross-inspection dependency scoping enforced by the UI picker" a real, load-bearing guard (different `inspection_id`s), not a guard against something that couldn't happen.
- **`status`**: `text not null default 'not_started'` + CHECK constraint (`not_started`/`scheduled`/`in_progress`/`blocked`/`done`/`qc_needed`) — matches the existing `condition`/`assigned_to` convention (0001_init.sql, 0006_assigned_to_other.sql) and the existing `is_manual_addition boolean not null default false` default pattern on this same table, rather than a native Postgres ENUM (new pattern, painful to alter later).
- **`blocks_line_item_id`**: nullable self-FK, `on delete set null` (deleting a predecessor clears the dependency instead of the delete failing with a raw constraint-violation error against the existing Remove Section flow), plus a CHECK preventing self-reference (`blocks_line_item_id is null or blocks_line_item_id != id`). Cross-inspection references are prevented by UI scoping only (no DB trigger) since the picker only ever lists same-inspection items.
- **Cycle detection**: `updateLineItemSchedule` walks the existing chain before saving a new `blocks_line_item_id` and rejects anything that would create a cycle (A→B→A) — cheap at this table's real per-inspection row count (~10-20), and nothing at the DB level catches this on its own.
- **Kept single-predecessor** (not a many-to-many join table) after a second, sharper challenge from outside-voice review (the demand evidence itself describes multi-trade gating) — chained single-predecessor links can represent "C waits on both A and B" as two separate links, which covers the common 2-3-trade case without a join table. Not re-opened again without new evidence from real usage.
- **New dedicated server action** (`updateLineItemSchedule`) owns these 4 fields — separate from `bulkUpdateLineItems`, which owns every other field on the inspection detail page's form. Avoids coupling two different pages' forms to one action.
- **`duplicateLineItem` resets status/dates** on the new row (`not_started`, null dates, null `blocks_line_item_id`) rather than carrying the original's schedule forward — a duplicated line item is a distinct, newly-noticed task. Flagged explicitly as an implementation task below since this function's explicit `INSERT` column list has needed manual updates for every new `line_items` column before (already happened for `vendor_id`, `labor_hours`, `still_image_file`).
- **Row order**: grouped by `room_area` (matches the inspection detail page, Turn Scope sheet, and Move Out Report), `scheduled_start` as secondary sort within each room; unscheduled items fall back to insertion order.
- **Self-reference validated in the action**, not left to the DB CHECK alone — returns a clear message instead of surfacing a raw Postgres constraint violation.
- **Interaction model: drag-to-reschedule bars** (revised from the original design doc's implicit assumption of a static/form-only view, after outside-voice review flagged this as undefined). This is a genuinely new client-interaction pattern for this codebase — every other view here is a plain form with an explicit Save button — and needs optimistic client state plus fast per-item commits on drag-end. **Effort/Risk revised from S-M/Low to M/Medium** to reflect this; it is the single biggest cost driver in this plan now.
- **`inspections.status` and the new `line_items.status` are independent by design**, no gating between them — the former tracks the review-document lifecycle (has Jessica signed off), the latter tracks the physical job lifecycle (has the work happened), and GPM's real workflow already has job work continuing well after/independent of the inspection being reviewed or exported.
- **Vendor/GPM-crew sequencing conflict — the tool doesn't reach vendors in v1.** Confirmed as an accepted gap: even with perfect internal staff adoption, the specific cited failure (a vendor and a crew stepping on each other) isn't directly prevented, since vendors still get their schedule window exclusively by Courtney's phone call, same as today. Shared internal visibility should reduce (not eliminate) the failure by letting staff catch a bad window before it becomes a conflict. Already tracked as a deferred Open Question (vendor-facing access); this just confirms that gate is load-bearing, not cosmetic.
- **No auth/session system exists anywhere in this app** (verified: `dashboard/app/login/page.tsx` is explicitly a decorative placeholder — "no user/session model exists yet, so this screen does not gate access"). "Staff-only" for this feature is a workflow convention, not an enforced boundary — any anonymous visitor with the URL can already read/edit everything in this app today, and this plan adds job-scheduling data to that same surface. Treated as a pre-existing, whole-app gap, not something this PR fixes — logged to TODOS.md.
- **This repo has zero automated tests** (no framework config, no test script, 0 test files) despite handling live financial data. Adding Vitest and testing only the new code this plan introduces (not retroactively testing the rest of the app).

## Design Review Decisions (2026-09-11, /plan-design-review)

Visual/interaction decisions made against the drag-to-reschedule Job Timeline, after two critical DESIGN.md violations were found in the first mockup pass:

- **Job status renders as plain text, no color-coding.** The first mockup pass reused condition/accent color tokens (error red, ochre, neutral gray) for job status — DESIGN.md reserves those four colors exclusively for `line_items.condition` and explicitly forbids a second meaning for the ochre accent. Fixed: status is a plain text label, no new palette.
- **Assignee type (GPM Staff/Outside Vendor/Other) shown as a text label inside the bar, not a fill color.** The first pass invented a blue not in DESIGN.md's palette for "Outside Vendor," reading as repurposed brand-indigo (logo-mark-only, explicitly forbidden in app chrome). Fixed: every bar renders in the same neutral gray; assignee type is text.
- **Blocked/at-risk items get the loudest visual treatment on the page** (a diagonal hatch in the existing `error` token), reversing the original hierarchy where a reviewer's actual highest-priority signal (a blocked job) was the quietest element (a 6px dot) while a lower-stakes attribute (assignee type) was the loudest (a saturated color fill).
- **Dependency (`blocks_line_item_id`) is shown as a small bordered "← blocked by: X" indicator in the item cell, hover/click to highlight the referenced bar — not a drawn connector line.** The original plan's drawn-line approach only had a defined look for the trivial same-row/adjacent-time case; real dependencies are routinely cross-room and cross-time, which a straight line at one y-coordinate can't represent without solving routing, z-index-over-intervening-bars, and off-screen/scroll problems nobody scoped. This also simplifies the eng-review implementation task (T4) substantially — no SVG routing needed.
- **Keyboard/accessibility: dates stay editable via plain date-input fields, in addition to dragging.** Drag-to-reschedule (the scope decision from eng review) had no keyboard-accessible alternative specified — DESIGN.md's own accessibility bar and this app's own convention (every field elsewhere is a plain input) require one. Resolves eng review's Tension 8 more cleanly than either original option: both the drag interaction and full keyboard parity ship together, not one or the other.
- **Drag-state shadow is now an explicit, licensed extension of DESIGN.md's floating-control shadow exception** (previously the only named exception was "theme toggle / floating controls") — a dragged bar counts as temporarily floating under the same logic; add this line to DESIGN.md's own Decisions Log when implementing.
- **Empty/unscheduled state**: a line item with no `scheduled_start`/`scheduled_end` yet renders a dashed-border track with an italic "Not scheduled" placeholder — not a blank void (most items on a freshly-generated timeline will be in this state).
- **A "today" marker (thin vertical ochre line) crosses the axis and all rows; the visible date range is computed from the actual min/max scheduled dates across all line items (plus today), not a fixed 2-3 week window** — so nothing is ever silently off-screen.
- **Drag-end commit failure and invalid-drop (dependency violation) both revert the bar to its last saved position with a brief inline message near the row — no toast**, matching DESIGN.md's existing no-toast status-change philosophy. This closes the critical gap eng review flagged (drag-end failure had no defined error handling).
- Interaction states table (empty/error/invalid-drop/hover) added to the Test Plan Artifact.
