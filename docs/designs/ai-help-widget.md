## Problem Statement

Chris asked for "an AI driven help tool that shows on the bottom left of each page." No
further detail given initially -- this doc records the scoping conversation that turned
that into a buildable v1.

## Status Quo

Confirmed: when Jessica (the reviewer) gets stuck on a page or a field, she asks Chris
directly. He is the de facto help desk today -- a real, ongoing cost of his time, and a
hard block when he's unavailable.

## Target User & Narrowest Wedge

Target user: Jessica, the daily reviewer. Confirmed her questions split roughly evenly
between two kinds:
- Workflow ("how do I add a bulk item", "where's the Take-Off Sheet")
- Data-specific ("why does this total show $80", "why didn't this line item match")

Chris explicitly chose to build BOTH from day one, not defer the data-specific half --
a fixed FAQ-only bot would leave half of Jessica's real questions unanswered.

## Constraints

- No existing help content of any kind exists in the app (no docs site, no FAQ) --
  workflow answers need a written reference created from scratch.
- The widget renders on every page load; cost/latency per query matters even though
  usage volume is low (internal tool, handful of users).
- No AI vendor credential exists for this use case yet (Gemini is wired in for an
  unrelated purpose -- video-to-line-item extraction).

## Premises

1. Needs a new `ANTHROPIC_API_KEY` credential -- Claude isn't currently used anywhere
   in this codebase.
2. Must know both the current page AND the real data on it per request, not just a
   static FAQ, since data-specific questions are half of the real demand.
3. Workflow-help content has to come from a reference doc I write describing each
   page/feature -- nothing exists to point the AI at otherwise.
4. Cheap/fast model (Claude Haiku), called only when the reviewer actually asks a
   question -- never on page load itself.

All four agreed by Chris without revision.

## Approaches Considered

### Approach A: Tool-calling (Claude looks up data itself)
Claude gets a small set of DB-lookup tools it can call on demand, plus the written
workflow reference. Scales to new pages automatically. Rejected for v1: real design
work to get tool selection reliable, slower round-trip per data question.

### Approach B: Every page hands over its own data
Each page passes its already-fetched data into the widget as a prop. Rejected: touches
every existing page now and needs remembering on every future page forever -- the exact
"forgot to update it" failure already logged twice in this codebase (`duplicateLineItem`
silently dropping new columns three separate times).

### Approach C: Central URL→data map (chosen)
One new file maps each page's route pattern to a query for "what's relevant to this
page." No tool-calling, no per-page retrofitting.

## Recommended Approach

**C.** Delivers real-data-aware answers from day one without B's distributed
maintenance tax, and ships faster than A while leaving room to add tool-calling later
if the fixed-context approach proves limiting on a specific page.

## Architecture (v1)

- **UI**: a small floating button, bottom-left, present via `AppShell` (one mount point
  covers every page automatically, same pattern as the nav rail). Click opens a chat
  panel. Client component, local state only (open/closed, message history) -- no
  persistence needed for v1.
- **Server action**: `askHelpAssistant(pathname, question, conversationHistory)`.
  Looks up `pathname` against a route-pattern map (e.g. `/inspections/[id]/quote-sheet`
  → fetch that inspection's line items/totals/bulk materials), bundles matched data +
  the written workflow reference + the question into one Claude Haiku call, returns
  the answer.
- **Context map**: new `lib/helpContext.ts` -- one function per route pattern, each
  returning a small, already-summarized data snapshot (not raw table dumps) for that
  page type. Falls back to "no page-specific data" (workflow-only) for unmapped routes,
  so a new page never breaks the widget -- it just doesn't get data-awareness until
  someone adds its pattern to the map.
- **Workflow reference**: new `lib/helpReference.md` (or similar), a written doc
  describing each major page/feature in plain language, injected into every prompt's
  system context alongside whatever page-specific data was matched.
- **Vendor**: Anthropic Claude Haiku (fast, cheap, good enough for Q&A), via the
  `@anthropic-ai/sdk` package -- new dependency, new `ANTHROPIC_API_KEY` env var.

## Open Questions

- Exact wording/scope of the workflow reference doc -- will be drafted during
  implementation and is easy to revise afterward, doesn't block starting.
- Whether conversation history persists across a page navigation (v1 default: no,
  resets per page load -- can revisit if that proves annoying in practice).

any page and get a correct workflow answer -- without asking Chris.
