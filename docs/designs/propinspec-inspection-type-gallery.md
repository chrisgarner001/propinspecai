## Problem Statement

PropInspec assumes every inspection is a move-out headed to a Quote Sheet. In reality GPM
runs move-in, condition-check, new-property, and pre-sale inspections too — and today those
still go through zinspector, in parallel, because PropInspec has no way to represent them.
There is also no way to actually page through an inspection's photos: "View Image Folder"
(`app/components/ImageShareGallery.tsx`) opens each thumbnail as `<a target="_blank">` to the
raw file — a new browser tab per photo, no next/prev, no in-app viewer.

## Demand Evidence

Zinspector is not legacy cruft being phased out on its own schedule — it's the **active
fallback for every non-move-out inspection today**, confirmed by the user directly: "Zinspector
is the fallback for non-move-out inspections specifically." That's a real, current, ongoing
cost: GPM maintains and pays for two inspection tools in production because PropInspec only
covers one slice of real inspection work.

## Status Quo

Chuck/Jessica run move-in, condition, and other non-move-out inspections entirely in
zinspector — PropInspec never enters the picture for that work. For photos specifically, even
on the move-out inspections PropInspec does handle, reviewing the full photo set means opening
each still individually in a new tab; there's no way to browse a room's photos as a set the way
zinspector's own report format does ("a photo gallery per item," per the original pipeline
design doc, `docs/designs/propinspecai-video-inspection-pipeline.md:44`).

## Target User & Narrowest Wedge

Chuck (field inspector) and Jessica (maintenance supervisor) are the two people who'd actually
stop opening zinspector if this shipped. The narrowest wedge, per the user directly: "Move-in
inspections... highest volume" — not a general configurable inspection-type/template system.

## Constraints

- No observation data exists yet for a move-in workflow in PropInspec — it doesn't exist to
  watch. This argues for the smallest real version, not a speculative full rebuild, so the next
  real move-in job becomes the observation opportunity that's currently missing.
- Single-tenant, GPM-first (established decision from prior sessions — see

## Premises

   configurable template system) — existing inspections default to `Move-Out`, nothing else
   changes for them. **Agreed, with scope refinement** (see below).
2. Build a real in-app photo gallery with next/prev paging, and capture a per-photo timestamp
   from the source video. **Agreed** — see Technical Finding below re: GPS.
3. Do NOT build per-type field customization, a different condition scale per type, or a
   move-in→move-out comparison view yet — that's guessing at requirements no one has observed.
   **Agreed.**

**Premise 1 scope refinement** (user, when asked what `inspection_type` should actually change
beyond being a label): hide the Quote Sheet / Tenant Chargeback Review / Move-Out Report
actions for non-move-out types (no replacement action takes their place — the detail page just
omits those three buttons for now), and add a type filter to the landing page (a plain
`<select>`, matching the existing search box's `<form method="get">` pattern; defaults to
showing all types, not Move-Out-only). Explicitly NOT in scope: a different status pipeline per
type — status stays unified for now.

**Migration:** additive, non-breaking — `inspection_type text not null default 'Move-Out' check
(inspection_type in ('Move-Out', 'Move-In'))` on `inspections`, same additive-column pattern as
every other migration in this repo (e.g. `0033_chargeback_and_billing_fields.sql`), with a real
CHECK constraint (not app-layer-only validation) so the value set stays enforced at the DB
level the same way `line_items.condition`'s check constraint already works in this schema.

**Delivery order note** (from adversarial review): the `inspection_type`/gating change and the

## Technical Finding: GPS is not recoverable from source video

The original pipeline design doc (`docs/designs/propinspecai-video-inspection-pipeline.md:45`)
flagged per-frame GPS/timestamp preservation as required "or this is a real regression." Before
committing to build it, two real GPM inspection videos were downloaded from Drive and probed
directly with ffmpeg (`ffmpeg -i <file>`, full metadata dump):

```
Metadata:
  creation_time   : 2026-09-09T17:26:33.000000Z
  com.android.version: 16
  com.samsung.android.utc_offset: -0400
```

Both files (Samsung Android recordings) carry a real `creation_time` tag but **no GPS/location
metadata at all** — confirmed absent, not merely unextracted. This is not a software gap: the
recording phone/camera app never embedded it, most likely because location tagging isn't
enabled in the Camera app's settings. Restoring GPS therefore requires a device-settings change
on GPM's end (worth raising with Chuck), not a code change.

**Sample size caveat:** only 2 files were probed, both Samsung Android, both from the same job
(121970, 2026-09-09) and almost certainly the same physical device. Every video filename
currently in `inspection_videos` (14 rows checked) follows the exact `YYYYMMDD_HHMMSS.mp4`
pattern — Samsung's default Camera app naming — consistent with a single device/fleet so far,
but not proof every GPM inspector's phone behaves identically (an iPhone, for instance, uses a
different metadata schema entirely). Treat "no GPS" as confirmed for the devices sampled and
likely representative of the current fleet, not as a guarantee for every future device — worth
a quick confirmation from Chuck on what phones are actually used for inspections.

**What the source data DOES support:** a real per-photo timestamp, computed as the video's
`creation_time` plus that frame's offset into the clip. This offset already exists in the data
flow today — `parseTimestampSeconds()` (`lib/stills.ts:26`) turns Gemini's `source_timestamp`
into the exact `seconds` value passed to `extractFrame(videoPath, seconds)` (`lib/stills.ts:49`,
called from `app/actions.ts`) — so `captured_at` is `creation_time + seconds`, no new timestamp
tracking needed, just reading a value that's already computed and reusing it.

**Timezone — simplified after review:** `captured_at` is stored as a plain UTC instant
(`timestamptz`) and always *rendered* against GPM's own fixed timezone, `America/Detroit`
(every property in this repo is Michigan-based, per
`docs/designs/propinspecai-video-inspection-pipeline.md`) — never the viewer's browser
timezone. This was originally drafted as "prefer the device's embedded UTC offset, fall back to
the fixed zone," but that path has no place to read a per-video offset from (nothing persists
it) and a raw numeric offset like `-0400` doesn't reliably map to a display abbreviation like
"EDT" without also knowing the exact date — the fixed-zone approach is strictly simpler,
already justified elsewhere in this doc, and standard IANA-aware date formatting
(`Intl.DateTimeFormat` with `timeZone: 'America/Detroit'`) produces the correct EDT/EST
abbreviation automatically from the UTC instant alone. A reviewer in a different timezone than
the property still sees what time it was *there* — that's the evidentiary fact that matters.

**Migration (`captured_at`):** additive, nullable — `alter table line_items add column if not
exists captured_at timestamptz;`. Null for every existing row until the backfill script (below)
runs, and for any future still whose video lacks a `creation_time` tag at all.

**Backfill:** source video is never stored by PropInspec itself — it's downloaded from Drive to
a temp path and deleted immediately after frame extraction (`app/actions.ts:984,1017`). Every
already-processed `line_items` row already persists both `source_timestamp` (the raw offset
string, e.g. `"0:42"`) and `source_video_drive_file_id` directly on the row (`app/actions.ts:
992-996`) — so a backfill script needs no re-derivation: for each row with `still_image_file is
not null` and `captured_at is null`, re-download that row's own video via
`source_video_drive_file_id` (same shape as `scripts/backfill-cost-embeddings.mjs`), reuse
`parseTimestampSeconds(source_timestamp)` for the offset (a pure function, already exists,
`lib/stills.ts:26`), and compute `captured_at`. **Failure mode:** if a Drive file has since been
deleted or moved, skip that row and log it rather than failing the whole run — matches this
repo's existing per-row-independent-retry pattern (`scripts/backfill-cost-embeddings.mjs`'s own
"still failing" count). This also means the backfill step has a real operational dependency —
Drive re-access per video, not just a DB migration — worth calling out under Dependencies below.

## Approaches Considered

*(Effort scale: S = well under a day, M = a few focused hours to a day, L = closer to a week.
Risk scale: Low = additive/reversible, well-understood pattern already used elsewhere in this
repo; Medium = new interaction pattern or a real chance of scope creep once started. This is a
design doc's rough sizing, not a sprint commitment.)*

### Approach A: Minimal — type field + gallery lightbox, no new tables
Add `inspection_type` (text + CHECK constraint, see Migration above) to `inspections` (default
`Move-Out`), gate the Quote/Chargeback/
Move-Out-Report actions and landing-page filter by it, and turn `ImageShareGallery`'s grid into
an in-page lightbox (next/prev) instead of new-tab links. Store `captured_at` per still at
extraction time, but don't surface it anywhere yet.
- Effort: S · Risk: Low
- Reuses: `ImageShareGallery.tsx`'s existing room-grouped grid, `still_image_file` pipeline.
- Con: leaves the evidentiary gap only half-closed — the timestamp exists in the DB but isn't
  visible anywhere a reviewer, tenant, or judge would actually see it.

### Approach B: Timestamp surfaced everywhere it matters (RECOMMENDED, chosen)
Same as A, plus the computed `captured_at` renders as a caption everywhere a still **already
renders today**: the gallery lightbox and the line-item hover preview (`EvidenceStill.tsx`).
**Correction, verified against the code:** the Move-Out Report PDF (`app/inspections/[id]/
move-out-report/route.ts`) does not embed photos at all today — it only queries
`room_area/item/condition/observed_evidence/recommended_action/tenant_charge*`, and its only
`doc.image()` call is the GPM letterhead logo. Adding photos to that PDF is real, separate scope
(PDFKit image sizing, page-break handling around embedded images) that was never actually
agreed to in this session — out of scope here, a candidate for its own future design doc if
GPM wants the report to carry photos, not assumed as part of this wedge.
Same caption format everywhere it does render — `Sep 9, 2026 5:26 PM EDT` (date + 12-hour time
+ timezone abbreviation, so "what time was this, *there*" is never ambiguous to a reviewer in a
different timezone).
- Effort: M (a few hours of focused work — new lightbox component, one migration, two
  caption-rendering call sites) · Risk: Low (well-understood UI pattern and two additive
  migrations)
- Closes the actual evidentiary gap (visible, not just captured) while staying inside the
  agreed narrow scope.

### Approach C: Full Move-In review mode with its own page (rejected)
`inspection_type` drives a bespoke Move-In review page — gallery-first, no Quote Sheet
language anywhere, styled around "get a feel for the property."
- Effort: L · Risk: Medium
- **Rejected**: this is the platform-before-observation trap Premise 3 explicitly ruled out —
  building a custom review experience before anyone has used even the simple version once.

## Recommended Approach

**Approach B.** Chosen by the user directly.

## Success Criteria

- A Move-In inspection can be created, reviewed, and its photos browsed end-to-end in
  PropInspec without opening zinspector.
- Existing Move-Out inspections are unaffected (default type, all current buttons/behavior
  unchanged).
- Every photo, wherever it renders today (gallery, hover preview), shows its actual captured
  timestamp for every video carrying a recoverable `creation_time` tag — confirmed present on
  every device sampled so far. Including stills extracted before this ships, once the backfill
  script has run (see Technical Finding). The Move-Out Report PDF doesn't render photos at all
  today (verified against the code) and stays that way — out of scope here, see Approach B.
- Clicking a gallery thumbnail opens an in-page viewer with next/prev — no more new-tab-per-photo.

## Dependencies

- None blocking for the going-forward path. Existing `still_image_file`/stills-extraction
  pipeline (`lib/stills.ts`) already runs per line item; this adds a timestamp computation
  alongside the existing frame extraction, no new external service.
- The one-off backfill script (for stills extracted before this ships) has a real operational
  dependency the going-forward path doesn't: re-accessing each video on Google Drive via its
  stored `source_video_drive_file_id`. If a file has since been deleted or moved, that row is
  skipped and logged, not treated as a hard failure (see Technical Finding).
