## Constraints
- Single-tenant: GPM's own purchase history only, matching the already-agreed single-tenant premise from the auth design doc. No multi-supplier or multi-company data model.
- Real financial document: suggestions must never silently write a cost — confirm-first, same rule as the shipped bulk-item-auto-fill (Premise 1, reconfirmed below).
- `cost_book_materials` (~1 test row today) gets replaced as the real data source, not kept alongside a separate hand-curated list (Premise 2 below).
- The CSV's "Job Name" column is inconsistent free text (samples: "113080 edgewood", "Rosedale", "personxl", "nick personal", "8") — **not** a reliable join key to `inspections.property_address` or `job_number`. No job-level purchase attribution in this wedge; noted as a possible future enhancement if that field is ever cleaned up, not promised now.
- `pg_trgm` and `vector` (pgvector) Postgres extensions are both available in the database (verified: `select ... from pg_available_extensions`) but not yet enabled — real, not hypothetical, options for the matching layer.
- **CSV structure (verified by reading the actual file, found during /plan-eng-review's later pass):** the file has a 5-line metadata preamble (Company Name/Phone Number/Source/Date Range/Export Date) plus one blank line before the real header row at line 7. The import script must skip these 6 lines, not assume line 1 is the header. Fields need real CSV-quote handling (`SKU Description` contains embedded `""` for inch marks, e.g. `"DIABLO 6-1/2"" 32T WOOD & METAL CSB"`) and currency-string parsing (`Original Unit Price`/`Net Unit Price` are `$24.97`/`$-2.25` style strings, not bare numerics) — a real CSV parser (e.g. a small dependency or Node's `csv-parse`) is required, not naive comma-splitting.
- **The same SKU Number can carry different `SKU Description` text across purchases** (observed in real data: SKU `161640` appears as both "2 in. x 4 in. x 96 i" and "2X4-96 KD-HT"). This is why "most recent description wins" was chosen for the aggregation grain — and it means a SKU's stored embedding can change over time as newer purchases arrive with different description text. Acceptable and handled by the inline-refresh rule below.

## Data Model (found during /plan-eng-review — the original draft named no tables/columns)
- **Extend `cost_book_materials` in place** (migration `0030`), not a new parallel table — it already has almost the right shape (`material_name`, `unit_price`, `unit`, `source`, `sku`, `last_purchased_date`, `notes`). Add: `purchase_count integer`, `price_min numeric(10,2)`, `price_max numeric(10,2)`, `embedding vector(768)`. The import performs an upsert keyed on `sku`, touching only rows where the imported SKU Number matches (existing manually-added rows with a different/no `sku`, e.g. non-Home-Depot materials, are left untouched — the existing manual add/edit UI in `app/cost-book/actions.ts` keeps working exactly as it does today, unmodified).
- **New raw import/audit table** `home_depot_purchase_history` — one row per CSV line. Columns match the CSV except `Company Name` (single-tenant, adds nothing) and `Program Discount Indicator` (always blank in the real data, not stored): `purchase_date`, `store_number`, `transaction_id`, `register_number`, `job_name`, `sku_number`, `sku_description`, `quantity`, `original_unit_price`, `department_name`, `class_name`, `subclass_name`, `program_discount_amount`, `other_discount_amount`, `extended_retail`, `net_unit_price`, `imported_at`. Exists for audit/provenance and so aggregates can be recomputed later without re-parsing the CSV. Unique constraint on `(transaction_id, sku_number, register_number)` with `on conflict do nothing` — makes re-running the import script on the same or an overlapping CSV export safe (dedup, not double-count).
- **Embedding model:** `gemini-embedding-001` via the existing `@google/genai` client (same pattern as `lib/gemini.ts`), `outputDimensionality: 768` (truncated via Matryoshka Representation Learning from the model's larger native size — 768 balances match quality against pgvector index size/speed at this data scale), `taskType: 'RETRIEVAL_DOCUMENT'` when embedding stored SKU descriptions, `taskType: 'RETRIEVAL_QUERY'` when embedding a Quote Sheet item name at suggest-time (Google's documented asymmetric-embedding pattern for retrieval). Migration `0030` must include `create extension if not exists vector;` — the extension is available in the database but not yet enabled (Constraints above); this is where it gets turned on. ~8,000 unique SKUs need embedding in the initial batch (counted from the real file) — sequential calls are fine given the null-on-failure + idempotent backfill safety net already in place; no special concurrency handling required for this wedge.
- **pgvector index:** HNSW, `vector_cosine_ops` (cosine distance — the standard metric for this embedding model's vectors).
- **Similarity threshold:** suggestions below 0.75 cosine similarity are not shown (no plausible match beats showing a bad one) — a tunable constant, expect to revisit once real suggestions are seen against real Quote Sheet item names.
- **Negative-price rows** (`Net Unit Price < 0` — returns/credits; a real example in the data is a row with `Original Unit Price` `$-34.98` and `Net Unit Price` `$-33.23`) are excluded when computing `unit_price`/`price_min`/`price_max` for a SKU, but still stored in the raw audit table as-is. `purchase_count` reflects only the non-negative rows that fed the price computation — a return doesn't count as an additional purchase.
- **Embedding failure handling:** if the Gemini embedding call fails during an upsert, the row still saves (price data lands regardless) with `embedding = null` — a null embedding just means that SKU won't surface in similarity search until re-embedded. A small idempotent "backfill missing embeddings" action (targets only `embedding is null` rows) can be re-run safely, not a blocking retry loop inside the import.
- **Embedding refresh scope:** the "regenerate on write" rule applies to the import and backfill paths only. The pre-existing manual add/edit UI (`app/cost-book/actions.ts`) stays genuinely unmodified per Premise 3 — a manually-added material (no `sku`, or a `sku` that never appeared in an import) simply has no embedding and won't surface via similarity search. That's an accepted gap for this wedge, not a bug: manual entries were never part of the "learn from purchase history" loop this design is about. Extending embedding generation to the manual UI is a small, separable follow-up if it turns out to matter.
- **Materials view at scale:** thousands of real rows replace the 1 test row. Add a search input (filters `material_name`/`sku` server-side) to the existing Cost Book Materials section; cap the default unsearched view at the ~200 most-recently-purchased rows rather than building full pagination for this wedge.
- **Ongoing purchases after this one-time import:** this is a historical backfill, not a recurring automated sync. Chris re-exports a fresh CSV from Home Depot Pro Xtra and re-runs the (idempotent) import script manually when he wants to refresh the data — no scheduled job in this wedge. Revisit if that manual cadence turns out to be a real burden.

## Approaches Considered (matching layer)

### Approach A: Postgres trigram search only (pg_trgm)
Pure SQL character-similarity matching (`similarity()`/`%` operator on a GIN trigram index), no AI cost. Effort: S (human ~1 day / CC ~1-2 hrs). Risk: real chance of poor match quality against heavily-abbreviated real HD text (e.g. "DIABLO 6-1/2" 32T WOOD & METAL CSB" for what a reviewer would type as "circular saw blade") — trigram similarity is character-level, not semantic, and HD's own SKU descriptions abbreviate aggressively.

### Approach B: Embeddings + pgvector (CHOSEN)
One-time: generate embeddings for each unique SKU description (Gemini's embedding API — `@google/genai` already a dependency) and store them (pgvector). At suggest-time: one cheap embedding call for the Quote Sheet item's name, then a fast pgvector nearest-neighbor search against the stored vectors. Effort: M (human ~2-3 days / CC ~3-5 hrs). Good semantic matching ("Kitchen Faucet" finds abbreviated HD variants that share no characters) without adding a slow/costly generative AI call to every Quote Sheet page load — only a single small embedding call per lookup, not a full LLM round-trip.

### Approach C: Trigram pre-filter + Gemini re-rank (rejected for now)
Cheap SQL narrows to ~20 candidates, then one Gemini generative call ranks/picks the best matches using item context. Reuses the Gemini pattern already in this codebase (video→line-item extraction), but adds a real generative-AI call (slower, costlier) to the suggestion flow instead of a fast embedding lookup. Rejected: Approach B gets comparable quality at lower latency/cost per lookup.

## Recommended Approach
Approach B (embeddings + pgvector). Chosen by Chris.
